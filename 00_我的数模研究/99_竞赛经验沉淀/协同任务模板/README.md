# 协同任务模板 · 三手分工制

> 从华数杯B题VLSI竞赛作品中抽象的标准化协同工作流程
> 方法论来源：565文件深度复盘（建模手31/编程手358/论文手166）
> 适用场景：数学建模竞赛、科研项目、需要多人协作的复杂任务
> 协作方式：UGit / Git 版本控制

---

## 一、这是什么？

这是一个**开箱即用的协同任务文件夹模板**。把它复制到你的项目目录，改个名字，就可以开始三手分工协作了。

**核心思想**：模拟三人团队（建模手/编程手/论文手），每个人独立工作，通过"移交-反馈"机制保证质量。

---

## 二、目录结构

```
项目名/
├── 00_任务总控/          ← 所有人共享，任务的"大脑"
│   ├── 任务说明.md         题目/目标/分工/截止时间
│   ├── 进度看板.md         谁在做什么，完成了什么
│   ├── 权威数字表.md       修正后的关键数据（所有人引用这个）
│   └── 时间线.md           各阶段时间安排
├── 01_背景研究/          ← 赛前/题后深度研究
│   └── 背景全量研究报告.md  问题本质/标准解法/已知坑
├── 02_建模手/            ← 数学建模（建模手专属）
│   ├── 建模手总纲.md       整体建模思路
│   ├── 实践反馈融入.md     编程手反馈后的修正
│   └── Q1/ Q2/ Q3/ Q4/   每问独立建模
├── 03_编程手/            ← 代码实现（编程手专属）
│   ├── 代码库/             可复用的核心代码
│   └── Q1/ Q2/ Q3/ Q4/   每问独立编程
├── 04_论文手/            ← 论文写作（论文手专属）
│   ├── 配图/               所有图表
│   ├── 工具/               md2docx等工具脚本
│   └── Q1/ Q2/ Q3/ Q4/   每问独立写作
├── 05_辅助文档/          ← 参考论文/数据/素材
├── 06_交付物/            ← 最终提交的论文/代码/附件
└── 99_归档/              ← 旧版本/废弃方案（不乱档的关键）
    ├── 旧版本/             文档的历史版本
    └── 废弃方案/           被证伪的思路/代码
```

## 三、三手职责

| 角色 | 核心职责 | 工作目录 | 产出物 |
|------|---------|---------|--------|
| **建模手** | 问题形式化、数学推导、算法选型、陷阱分析 | `02_建模手/` | 深研笔记、公式表、移交清单 |
| **编程手** | 数据解析、算法实现、实验运行、结果验证 | `03_编程手/` | 代码、实验数据、问题反馈 |
| **论文手** | 论文组织、写作润色、可视化、最终排版 | `04_论文手/` | 正稿、配图、最终论文 |

**协作原则**：
- 每个人只在自己的目录下工作，避免冲突
- 共享信息放在 `00_任务总控/`
- 建模→编程通过"移交包"传递信息
- 编程→建模通过"反馈文档"传递问题

## 四、工作流程（什么时候干什么）

### 阶段0：任务启动（0-2小时）
- **所有人**：读题，讨论，填写 `00_任务总控/任务说明.md`
- **建模手**：开始 `01_背景研究/背景全量研究报告.md`
- **输出**：任务分工、时间线、背景研究初稿

### 阶段1：建模（2-8小时）
- **建模手**：按问建模，每问产出标准文件集（见 `02_建模手/README.md`）
- **编程手**：准备环境，解析数据，写基础工具
- **论文手**：收集参考论文，定论文骨架
- **输出**：建模手总纲、各问建模文档

### 阶段2：编程实现（8-20小时）
- **建模手**：完成建模后，打包"移交包"给编程手
- **编程手**：按移交清单实现，每步写【思路】，发现问题及时反馈
- **输出**：可运行代码、实验结果、问题反馈

### 阶段3：反馈修正（20-24小时）
- **建模手**：融入编程手反馈，修正理论，更新 `权威数字表.md`
- **编程手**：根据修正后的模型调整代码
- **输出**：实践反馈融入文档、修正后的权威数据

### 阶段4：论文写作（24-48小时）
- **论文手**：按问写作，每问自成闭环，多版本迭代
- **建模手/编程手**：提供素材，审核技术准确性
- **输出**：论文正稿、配图

### 阶段5：交付（48-72小时）
- **所有人**：最终检查，排版，提交
- **输出**：`06_交付物/` 中的最终论文、代码、附件

## 五、版本管理规范（不乱档的关键）

### 5.1 文档版本命名
```
当前版本：正稿.md（不带版本号，永远是最新的）
历史版本：正稿_v1.md、正稿_v2.md（归档到 99_归档/旧版本/）
废弃方案：XXX_废弃.md（归档到 99_归档/废弃方案/）
```

### 5.2 什么时候归档？
- 文档有重大修改时，先把旧版复制到 `99_归档/旧版本/`，再改当前版
- 方案被证伪时，不要删除，移到 `99_归档/废弃方案/`，并注明为什么废弃
- 最终交付后，所有中间版本归档

### 5.3 代码版本
- 核心代码放在 `03_编程手/代码库/`，作为可复用模块
- 每问的实验代码放在 `03_编程手/QX/`
- 用Git管理代码版本，不需要手动复制旧版本

## 六、UGit协作指南

### 6.1 分支策略
```
main        最终交付版本（保护分支，只合并不直接改）
├── dev     开发主分支
│   ├── modeling   建模手分支
│   ├── coding     编程手分支
│   └── writing    论文手分支
```

### 6.2 提交规范
```
[建模手] Q1：完成B*-Tree表示法推导
[编程手] Q2：修复HPWL计算bug，线长从295k降到220k
[论文手] Q1：正稿v2，补充灵敏度分析
[总控] 更新权威数字表，修正死区比例
```

### 6.3 协作纪律
1. **每天至少pull一次**，避免冲突累积
2. **只在自己的目录下提交**，不要改别人的文件
3. **共享文件（00_任务总控/）修改前先沟通**
4. **大文件（图片>1MB、数据>10MB）用Git LFS**
5. **提交信息写清楚做了什么**，不要写"更新""修改"

### 6.4 冲突处理
- 同一文件被多人修改时，先沟通谁的版本为准
- `00_任务总控/权威数字表.md` 是唯一权威数据源，冲突时以最新实测为准

## 七、快速开始

1. **复制模板**：把整个 `协同任务模板/` 文件夹复制到你的项目目录
2. **重命名**：改成项目名（如 `2026_国赛A题`）
3. **初始化Git**：`git init`，创建dev分支和各角色分支
4. **填任务说明**：打开 `00_任务总控/任务说明.md`，填写题目和分工
5. **开始工作**：按工作流程推进

## 十、一句话

> **三手分工不是把任务切成三块，而是让三个独立视角互相验证。建模手的理论要被编程手的实践检验，编程手的代码要被论文手的写作拷问。最终交付的不是某个人的成果，而是三方碰撞后的结晶。**
